# ROAD LIVE — продуктовый план и спецификация реализации

Дата: 19.10.2026. Статус: проектирование следующей итерации; НЕ означает завершение реализации.

## 1. Продукт

Живая карта дорожной обстановки и взаимопомощи водителей. Пилот: Новосибирск. Главные задачи: (1) узнать, что происходит рядом; (2) быстро и безопасно сообщить о ситуации; (3) получить/предложить помощь. Уникальность — доверие к свежести сообщений и ответ на SOS, а не дублирование полноценного навигатора.

**Не создавать новый стек.** Существующая база: React, TypeScript, Vite, Yandex Maps JS, Express API на Vercel, Supabase, Telegram Mini App + web-login, Web Push / PWA.

## 2. Аудит обнаруженного кода

- src/components/map/RoadMap.tsx: Яндекс карта, светлая/тёмная тема, собственные SVG-пины, кластеризация, pin picker.

## 3. Экранная структура

### Карта (главная вкладка)

- Полноэкранная интерактивная карта, переключатель темы, кнопка «Моё местоположение».
- Компактная горизонтальная строка фильтров: Все, ДТП, ДПС, Опасности, Дорога, SOS; остальные категории в дополнительном списке.
- Маркеры компактные, одной визуальной системы, без эмодзи. Группировка при отдалении, без перекрытия геометрии улиц.
- Нажатие на точку => нижняя карточка: название, время, расстояние, статус достоверности, фото, действия «Подтвердить» / «Уже нет» / «Комментировать».
- FAB «Сообщить». Отдельная визуально заметная, но компактная кнопка SOS.
- Гость видит карту, список и карточки; любые изменения только после серверно проверенной Telegram-авторизации.

### Сообщить о событии

1. Выбрать тип и подтип.
2. Предложить GPS-точку; для обычных событий разрешить вручную переместить маркер, для SOS требовать реальный свежий GPS.
3. Показывать итоговую точку и пояснение о направлении движения.
4. Проверить дубликаты в радиусе 250 м; предложить подтвердить существующую запись.
5. Публиковать после проверки доступа; обновление карты сразу, затем согласование с ответом сервера.

### SOS / взаимопомощь

1. «Нужна помощь» -> аккумулятор, колесо, топливо, трос, снег/грязь, другое.
2. Показывать точку, точность GPS, текст запроса и предупреждение, что адрес увидят другие.
3. Сервер проверяет Telegram-сеанс, географию, лимиты запросов и активный SOS.
4. Создаётся запись со статусом открытого запроса; пользователи в подходящем радиусе получают уведомление.
5. Помощник выбирает «Помогу бесплатно», «За оплату» или «Обсудить», автор принимает одно предложение.
6. Создать приватный диалог участников, обновлять статус: ищем помощь -> помощник выбран -> помощь в пути -> завершено/отменено.
7. Обе стороны подтверждают выполнение; отдельная жалоба на мошенничество. Для опасности жизни — текст «112», сервис не заменяет экстренные службы.

### Лента, сообщения, профиль

- Лента запросов и событий с фильтрами «Рядом», «Требуется помощь», «Новые».
- Личные диалоги только с участниками связанного SOS. Не показывать чужие личные контакты без согласия.
- Профиль: имя из Telegram, вклад, подтверждения, благодарности, репутация, жалобы, настройки города, GPS и уведомлений.

## 4. Справочник категорий и TTL

Сохранить действующий единый модуль src/utils/eventTtl.ts, не создавать второй в UI.

| Тип | Без подтверждения | После подтверждения |
| --- | ---: | ---: |
| ДПС | 15 мин | 25 мин |
| ДТП | 20–30 мин | 45–60 мин |
| Переезд | 20 мин | 20 мин |
| Опасность | 20 мин | 40 мин |
| Светофор | 45 мин | 90 мин |
| Дорога, обычная | 60 мин | 360 мин |
| Ремонт / яма | 120 мин | 2880 мин |
| SOS | 30 мин | 60 мин |

Для SOS отдельное требование: за 5 минут до автоистечения отправлять автору запрос «Помощь ещё нужна?», давать продлить одним действием, закрывать вручную с подтверждением. Иначе живой SOS может преждевременно исчезнуть.

## 5. Контракты данных и API

Сохранить основные сущности profiles, road_events, event_confirmations, event_comments, event_assistance_offers, driver_locations, push_subscriptions. Конкретные SQL-миграции создавать только после сверки действующей схемы.

- GET /api/public/events: публичные безопасные данные, без Telegram ID, адреса аккаунта, телефонов, истории GPS.
- GET /api/events: авторизованная выборка с server-side status/TTL.
- POST /api/events: создать событие, проверка owner из сессии, type, координат, текста, лимитов.
- POST /api/events/:id/confirm: одна реакция на пользователя, server-side ограничения и веса.
- POST /api/events/:id/resolve: закрывает автор или разрешённый исполнитель по правилам.
- POST /api/events/:id/offers: предложение помощи с защитой от спама.
- POST /api/events/:id/offers/:offerId/respond: принять/отклонить, транзакционно только одну принятую заявку.
- POST /api/drivers/location: только с согласия, GPS-точка и серверная временная метка; не публиковать чужие координаты.

Названия эндпоинтов выше — целевые контракты. Перед работой сравнить с уже существующими маршрутами server.ts и переиспользовать их без несовместимых дублей.

## 6. События, геолокация, пуши

- Никогда не брать центр карты как реальный GPS пользователя; координаты проверять на клиенте И сервере.
- Реальное расстояние считать географически корректно: PostGIS geography с индексом и ST_DWithin либо эквивалентной проверенной функцией.
- Активная точка: использовать только недавние GPS-данные, например возраст не более 10 минут для срочных уведомлений; выбор границы закрепить тестами.
- Пользователь может выключить передачу GPS и удалить сведения о местоположении/Push-подписке.
- Радиусы: базовые предупреждения 2 км, SOS 5 км; расширенные настройки 5/15/30/50 км — после сверки с действующими полями БД, чтобы настройки не противоречили серверной доставке.
- Уведомлять лишь тех, кто подходит по радиусу/категории и дал разрешение; не уведомлять автора, не отправлять один и тот же push повторно.
- Telegram-бот как дополнительный канал там, где есть разрешённый чат/подписка; Web Push через стандартный Service Worker.
- На iOS Web Push поддерживается для веб-приложений, добавленных на домашний экран. В обычной вкладке Safari нельзя обещать такой же сценарий.
- Работа GPS в фоне в обычном веб-приложении не гарантируется: не обещать непрерывное фоновое слежение или автоматические уведомления по свежему местоположению без открытого приложения.

## 7. Достоверность, безопасность и приватность

- Новая метка = «Не подтверждено», далее «Подтверждено N водителями», «Устаревает», «Снято».
- Вес GPS-подтверждений рядом может быть выше, но GPS — сигнал, а не доказательство истинности.
- Один пользователь не должен подтверждать свою метку как независимый свидетель.
- Ограничить число публикаций и SOS, отсекать спам, ложные сообщения, дубли и частые переключения статуса.
- Репутация зависит от подтверждённых событий, действительной помощи и проверенных жалоб. Не начислять баллы только за количество публикаций.
- Не показывать перемещения/последнюю позицию водителя другим пользователям, кроме явной точки опубликованного SOS.
- Публикации о ДПС/камерах являются пользовательскими сообщениями об обстановке, а не советами по незаконному уклонению от контроля.
- Согласие на обработку геолокации и удаление данных — обязательный юридический/продуктовый пункт для рынка РФ.

## 8. Технические и юридические риски

1. Supabase roadlive сейчас INACTIVE; реализацию можно проектировать и кодировать, но проверки с реальными данными невозможны до восстановления.
2. Бесплатная лицензия Яндекс Карт предусматривает ограничения, в частности на мониторинг транспорта и сотрудников, сохранение данных API и перекрытие атрибуции. Проверить применимость коммерческой лицензии. Собственные сообщения пользователей — отдельные данные, не полученные от API карт.
3. Публичный ключ Yandex в клиентском JS не является секретом в смысле серверного токена, но ограничение доменов и расхода следует настроить.
4. Проверять подписанные Telegram initData на сервере, никогда не доверять initDataUnsafe.
5. Секреты Telegram bot, Supabase service-role и VAPID private — только на сервере.
6. На Vercel серверный WebSocket/постоянные фоновые процессы не предполагаются: API + фоновые задачи вне request scope + polling/Supabase Realtime там, где поддерживается.
7. Прямые сообщения и SOS могут использоваться для обмана. Нужны блокировка, жалобы, журнал решений модератора.

## 10. Приёмочные сценарии

- Гость открывает карту без Telegram; видит события и карточку, но POST запрещён.
- Вошедший пользователь ставит ДТП в точке X: после сохранения метка остаётся ровно в X, кликается, переживает перезагрузку.
- Водитель подтверждает событие рядом; другой водитель не может многократно повысить счётчик.
- Новый SOS пользователя A зафиксирован по свежему GPS; B в 4 км и включённым SOS-пушем получает уведомление, C в 8 км при радиусе 5 км не получает, A не получает собственное.
- Отключённый GPS и устаревший GPS не получают ложные «рядом».
- Принятие одного предложения помощи отклоняет конкурирующие одновременные решения без двойного назначения.
- Закрытый / истёкший / скрытый и модерированный инцидент не показывается на публичной карте.
- На мобильном пользователь может работать одной рукой; карта не закрыта большими баннерами.
- В браузере без Telegram нельзя создавать событие через ручной API-вызов с подставным userId.
- Включена атрибуция Яндекс Карты и кнопка перехода в Яндекс Карты в рамках лицензии.

## 11. Метрики пилота

Измерять: количество уникальных активных водителей в городе, ежедневные свежие события, долю подтверждённых событий, долю ложных сообщений, время до первой реакции на SOS, долю SOS с реальной помощью, долю успешной доставки push и удержание 7-го дня.

Первый запуск — Новосибирск, ограниченная пилотная группа. Без искусственных «живых» меток и фальшивых рейтингов.
